## Database migration — `migrations/003_auth_enhancements.sql`

New file. Creates:

- **`password_reset_tokens`** table (id, user_id FK, token_hash UNIQUE, expires_at, created_at) — separate table so multiple reset requests can coexist
- **`email_verification_tokens`** table (same shape) — same rationale
- **4 new columns on `users`**: `email_verified` (boolean, default false), `mfa_secret` (varchar, nullable), `mfa_enabled` (boolean, default false), `mfa_pending` (boolean, default false)

## Key flow changes

**Signup** now returns `{ user, tokens, emailVerificationToken }`.

**Login** with MFA enabled returns `{ mfaRequired: true, mfaToken }` instead of `{ user, tokens }`. Client then POSTs to `/mfa/verify` with `{ code, mfaToken }` to get tokens.

**MFA verify** handles two contexts via JWT `purpose` claim: `'mfa'` = login flow (issue tokens), no purpose = setup confirmation (set `mfa_enabled = true`).

## Security notes

- Forgot-password always returns 200 regardless of whether email exists (no enumeration)
- Reset tokens are single-use, deleted after consumption
- Password reset invalidates all refresh tokens for that user
- MFA token JWT expires in 5 minutes
- All tokens stored hashed (SHA-256), raw only in API response
- Rate limiting on sensitive endpoints (5/min per IP)
